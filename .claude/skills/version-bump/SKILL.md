# Version bump หลังแก้โค้ด

เว็บนี้ใช้ semantic versioning `MAJOR.MINOR.PATCH` จาก `version` ใน `package.json` (`APP_VERSION` อ่านจากตรงนี้และแสดงบน header / หน้าตั้งค่า)
ทุกครั้งที่ทำงานที่แก้โค้ดของเว็บเสร็จ ให้ทำตามขั้นตอนนี้ **ก่อน** สรุปงานให้ผู้ใช้

## 1. ดูว่างานนี้แก้อะไรไปบ้าง

- นับเฉพาะสิ่งที่แก้ใน **คำสั่งงานครั้งนี้** ไม่นับงานก่อนหน้าที่ยังไม่ได้ commit (งานก่อนหน้า bump ไปแล้ว)
- ถ้าจำไม่ได้ว่าแก้อะไรไป ดูจาก `git status` / `git diff` ประกอบกับสิ่งที่ทำในงานนี้

## 2. จัดระดับการเปลี่ยนแปลง

เลือกระดับ **สูงสุด** ที่เจอในงานนี้ (มีทั้งฟีเจอร์ใหม่และแก้บั๊ก = minor)

| ระดับ | ใช้เมื่อ | ตัวอย่างในเว็บนี้ |
| --- | --- | --- |
| **major** `X.0.0` | เปลี่ยนแบบที่ของเดิมใช้ต่อไม่ได้ หรือผู้ใช้ต้องปรับตัว/ย้ายข้อมูล | แก้ schema แบบลบ/เปลี่ยนชื่อคอลัมน์หรือตารางที่ต้อง migrate ข้อมูลเดิม, เปลี่ยนโครง URL จนลิงก์/bookmark เดิมเสีย, ถอดฟีเจอร์หลักออก, ยกเครื่อง UI ทั้งเว็บ, เพิ่มระบบ login ที่บังคับใช้ |
| **minor** `x.Y.0` | เพิ่มความสามารถใหม่ โดยของเดิมยังใช้ได้เหมือนเดิม | หน้าใหม่, เมนูใหม่ในหน้าตั้งค่า, ปุ่ม/ขั้นตอนการทำงานใหม่ (เช่น ย้ายของข้ามบ้าน, จัดการ tag), เพิ่มคอลัมน์/ตารางใหม่ใน schema แบบไม่กระทบของเดิม, เพิ่มตัวเลือกให้ฟีเจอร์เดิมอย่างมีนัยสำคัญ |
| **patch** `x.y.Z` | แก้บั๊ก หรือปรับเล็กน้อยที่ไม่ได้เพิ่มความสามารถใหม่ | แก้บั๊ก, ปรับ UI เล็กน้อย (จัดตำแหน่ง, ระยะห่าง, สี, ข้อความ), เปลี่ยนค่าเริ่มต้นเล็กน้อย (เช่น เลือกบ้านแรกให้อัตโนมัติ), refactor ที่พฤติกรรมไม่เปลี่ยน, ปรับ performance |
| **ไม่ bump** | ไม่มีอะไรเปลี่ยนในเว็บที่ deploy | แก้เฉพาะ `CLAUDE.md`, skill, README, comment ล้วน, `.env.example` |

กรณีก้ำกึ่งระหว่าง minor กับ patch ให้ถามตัวเองว่า "ผู้ใช้ทำสิ่งที่เมื่อก่อนทำไม่ได้ ได้แล้วหรือยัง" — ได้ = minor, ไม่ได้ = patch

## 3. ขยับ version

- ผู้ใช้ระบุเลข version มาเอง → ใช้เลขนั้นตามที่สั่ง ไม่ต้องวิเคราะห์
- bump **ครั้งเดียวต่อหนึ่งคำสั่งงาน** — ถ้าระหว่างงานเดียวกัน bump ไปแล้วแต่ภายหลังพบว่าระดับสูงขึ้น ให้แก้เป็นเลขของระดับที่สูงกว่าแทน ไม่บวกซ้ำ
- ขึ้นระดับไหน ให้รีเซ็ตเลขที่อยู่ทางขวาเป็น 0: `2.4.1` → major `3.0.0`, minor `2.5.0`, patch `2.4.2`
- แก้ให้ตรงกัน **3 ที่**:
  - `package.json` → `"version"`
  - `package-lock.json` → `"version"` บนสุด และ `packages[""].version`
- ถ้ามี npm ใช้ `npm version <major|minor|patch> --no-git-tag-version` ได้เลย (แก้ทั้งสองไฟล์ให้ และไม่สร้าง git tag) — ถ้าไม่มี npm ให้แก้ด้วย Edit เอง

## 4. แจ้งผู้ใช้

ในสรุปงานให้มีบรรทัดบอก version เสมอ พร้อมเหตุผลสั้นๆ เช่น

> version: 2.4.1 → 2.5.0 (minor: เพิ่มหน้าจัดการสถานที่ซื้อ)

ถ้าไม่ bump ก็บอกเหตุผลสั้นๆ เช่น "ไม่ขยับ version เพราะแก้แค่เอกสาร"
